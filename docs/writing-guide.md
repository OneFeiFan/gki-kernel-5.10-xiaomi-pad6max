# 文档写作规范

维护本仓库文档时遵守的规则。改代码、加补丁、发版本时，按最后一节的清单同步文档。

## 每个文件写给谁

| 文件 | 读者 | 写什么 | 不写什么 |
| --- | --- | --- | --- |
| `README.md` | 想用这个内核的人 | 是什么、功能、兼容性、安装与回退、文档索引、致谢 | 开发经过、构建细节、测试结果 |
| `CHANGELOG.md` | 想知道新版本改了什么的人 | 每个版本对用户可见的变化，以及发布前的验证结论 | 补丁编号、内部分支名 |
| `docs/features.md` | 用户和维护者 | 每个功能的作用、默认值、开关方法、注意事项 | 版本号、日期、调研过程 |
| `docs/known-issues.md` | 用户和维护者 | 已知问题、还没测够的改动、限制 | 已经修好的问题 |
| `docs/building.md`、`docs/verification.md` | 构建和发布的人 | 步骤、命令、通过标准 | 某一次的测试数据 |
| `patches/README.md` | 维护补丁的人 | 组织方式、依赖、补丁列表 | 功能说明（链接到 features.md） |
| 补丁说明头 | 维护补丁的人 | 出处、与来源的差异、KABI、依赖、验证范围 | |
| `docs/notes/` | 维护者自己 | 调研、实验和交接记录，标明日期 | |

同一件事只写在一个地方，其他地方用链接。比如 KMI 门禁的数字只写进 CHANGELOG 对应的版本，不在 README 和 features.md 里重复。

## 写作规则

**1. 先说结论，再说原因。** 读者第一句就应该知道这件事是什么、要不要关心。

- ✗ 2026-10-31 熄屏 3 分钟 A/B（8 核合计，单次采样，设备在充电），TEO 深睡占比 98.72%，qcom-cpu-lpm 97.74%，没有异常，功耗没测，默认保持厂商 governor。
- ✓ 默认的空闲调度器仍是厂商的 `qcom-cpu-lpm`。熄屏短测中 TEO 的深睡占比略高，实际功耗还没有测。

**2. 一句话只说一件事。** 不要用分号把四五个分句串在一起，不要括号里再套括号，不要用斜杠表示"和"或"或者"。

- ✗ 内核默认保持 stock：`cubic`、BFQ/cpq、zram 内建（Kconfig 默认 `lz4`，实际算法由系统或 yudi-tweaks 设置）、KSM 关闭、ADIOS 不作为默认。
- ✓ 内核的默认行为与原厂一致：拥塞控制是 cubic，KSM 关闭，IO 调度器是厂商设置的 cpq。zram 的压缩算法由系统设置，可以用 yudi-tweaks 更换。

**3. 参考文档里不写日期和构建序号。** 日期、r16 这样的序号只出现在 CHANGELOG 和 `docs/notes/` 里。功能变了就直接改功能说明，不在文档开头追加"某月某日更新"。

**4. 用通行的说法，不用内部黑话。** 英文只用于专有名词和代码标识符（KMI、zram、`call_rcu()`），不用口语化的英文词。

| 不要写 | 改成 |
| --- | --- |
| 灰度项 | 默认启用，仍在观察的改动 |
| 探针 | 直接说它是什么功能 |
| churn | 反复创建和删除 |
| hunk | 一段改动 |
| ABBA | 交替对比测试 |
| stock | 原厂 |
| 门禁全过 | 通过 KMI 门禁 |

**5. 不写防御性的说明。** 只写事实，不预先解释"这不是我们引入的""只归档、没有据此改动"。如果某个问题确实与本内核无关，写出原因即可。

- ✗ 这是 vendor 模块的问题，不是 r16 引入，功能正常。
- ✓ 原因在厂商的键盘驱动……原厂内核加载同样的驱动时也会报这条警告。

**6. 不用模板化的标题和提示语。** 不写"一句话现状""两个容易踩的点""注意："这类标题。需要提醒的内容，直接写成完整的句子放在相关段落里。

**7. 数字只写读者用得上的。** "设备开机加载了 419 个模块、369 个服务"对读者没有意义；"670 个厂商模块全部通过 CRC 检查"说明了兼容性，可以写。

**8. 表格只用于需要对照或查找的内容。** 默认值速查、补丁列表适合用表格；解释原因、描述流程用段落。

**9. 不确定的事情要说明不确定。** 没有验证过的推测，写成"可能""尚未确认"，并说明怎样验证。不要把推测写成事实。

**10. 不写面向 AI 会话的内容。** 不写"给接手的会话看""子代理""主代理"。文档的读者是人。

## 模板

### 功能说明（features.md）

```markdown
### 功能名

一两句话说明它做什么、对用户有什么用。

默认状态和开关方法。需要注意的限制或副作用。
```

### 更新日志（CHANGELOG.md）

```markdown
## r18（2026-11-05，已发布）

- 新增：用户能感知到的变化，一条一句。
- 修正：修了什么问题，影响是什么。

验证：一两句话写清通过了哪些检查。
```

未发布的版本标为"未发布"；只在本地构建的版本标为"本地构建"。

### 已知问题（known-issues.md）

```markdown
## 问题的简短描述

现象（用户会看到什么）。原因。影响范围。有没有绕过的办法。
```

### 补丁说明头

```
Origin: 来源仓库和提交；本地实现就写"本地实现"
Upstream-Status: Backport / Not-Upstream / Not-Applicable
KABI: none，或者占用了哪些预留字段
Depends-On: none，或者依赖的补丁编号和原因
Notes: 与来源的差异、合并了哪些旧补丁
Tested-On: 通过了哪些检查
```

## 提交信息

- 标题用英文，格式为"子系统: 做了什么"，不超过 72 个字符，例如 `zram: skip anonymous LRUs when swap is unavailable`。
- 正文说明为什么改、改了什么、怎么验证的。
- 不写"本次提交""该补丁"这类指代自身的话。

## 改动时的同步清单

| 改动 | 需要同步的文档 |
| --- | --- |
| 新增或删除补丁 | `patches/series`、`patches/series.xiaomi`、`patches/README.md` 的列表和依赖表、`source/`；有用户可见的变化时更新 `docs/features.md` |
| 改变默认值或开关 | `docs/features.md` 的速查表和对应章节；模块仓库的 README |
| 发现新问题或修好旧问题 | `docs/known-issues.md` |
| 构建或发布新版本 | `CHANGELOG.md`；发布到 Releases 时附上 CHANGELOG 对应的段落 |
| 改变构建或打包方法 | `docs/building.md` |
| 新增或改变测试方法 | `docs/verification.md`、`tools/README.md` |
| 调研、实验 | 写进 `docs/notes/`，文件名带日期；得出的结论再按上面的规则写进对应文档 |
